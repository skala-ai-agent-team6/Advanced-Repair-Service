# 2026-10-24 재고 조회 강제 요청 — 부품 조회 한도 도달 시나리오

## 최적화 항목 번호 — 2026-10-25 기준 정정

| 번호 | 호출 | 이번 작업 범위 |
|---|---|---|
| ① | 워커 `split_text` 소견 분리 GPT | 내가 제거할 대상. observation MCP는 유지 |
| ② | RAG 내부 중복 소견 정규화 GPT | 팀원 개선 항목. 최신 dev는 기존 정규화 결과를 재사용하며, V1 전체 진단에는 중복 호출이 남아 있음 (부품만 테스트는 미실행) |
| ③ | 부품 조회 한도 뒤 버려지는 GPT 도구 요청 응답 | 내가 개선할 대상. 필요한 최종 요약은 유지하므로 API 1회 감소를 보장하지 않음 |

**별첨(*) — RAG 최종 소견 GPT:** 기존에는 제거 후보였으나 현재는 유지한다. 최신 코드에서 리포트 입력에 전달되므로 제거 효과·품질을 별도 검증하기 전까지 이번 최적화 대상에서 제외한다.

호출 앞의 `01.`, `02.`는 실행 순서이고, ①~③ 및 별첨(*)은 위 항목 번호다.
항목 번호를 ①~③으로 통일하고 RAG 최종 소견은 별첨(*)으로 분리했다. API 횟수·시간·원본 JSONL은 변경하지 않았다. 최적화 코드는 아직 적용하지 않았다.


조회 한도에 걸리는 상황을 확인하기 위해 GPT가 계속 재고 조회를 요청하도록 강제한 전체 진단 테스트. 부품 확인에서 GPT 5회·실제 조회 4회가 발생했다.

- 접수 14 / 작업 13. 사진·소견 접수부터 실제 Spring·Kafka·MCP·OpenAI 전체 경로 실행.
- 이 접수에만 부품 도구 요청을 매번 강제했다(tool_choice=get_part_availability, parallel_tool_calls=false). 실제 모델 응답과 실제 재고 조회이며 자연 발생 시나리오는 아니다.
- 추가 사진 요청 0회, 진단 완료, 리포트 JSON·Markdown 저장 확인. 실제 재고 조회는 4회이고 5번째 부품 GPT 응답은 폐기됐다.
- 최적화 미적용. 테스트 후 일반 워커로 복원.

## 부품 확인은 왜 5회인가?

이번에는 **조회 한도에 걸리는 상황을 확인하려고 GPT가 계속 재고 조회를 요청하도록 강제했다.**

- GPT 요청 1~4회 → 실제 재고 조회 실행.
- GPT 요청 5회째 → 조회 한도 4회를 이미 써서 **실행하지 않고 버림**.

즉, **GPT 호출은 5회지만 실제 재고 조회는 4회**다. 버려진 5번째 호출이 개선 후보 ③가며, 일반 실행에서 항상 발생하는 것은 아니다.
