## 실제 측정 결과

| 시나리오 | V1 호출 / 전체 시간 | V2 호출 / 전체 시간 | 결과 |
|---|---|---|---|
| 일반 진단 | 8회 / 18.59초 | 6회 / 12.00초 | 추가 사진 0회, 리포트 생성 |
| 조회 한도 강제 진단 | 11회 / 16.19초 | 9회 / 12.65초 | 추가 사진 0회, 리포트 생성 |

- V2 첫 실행은 6회 / 50.46초였다. 모델·프로세스 초기 준비 지연이 포함된 실행으로 별도 보관하며 숨기지 않는다.
- API 감소 2회는 ① 소견 분리와 ② 중복 정규화 제거에 해당한다. ③은 이번 강제 실험에서 호출 횟수를 줄이지 않고, 마지막 응답을 정상 요약으로 바꿨다.
- 강제 시나리오: 실제 GPT가 get_part_availability를 계속 선택하도록 지정했다. 4회 조회 뒤에는 tool_choice="none"으로 정상 요약을 생성했다. 고정 응답으로 대신하지 않았다.
- 실제 Spring → Kafka → 이미지 모델·MCP·OpenAI → 결과 저장을 실행했다. 워커의 JSON·Markdown 리포트와 Spring의 SUCCEEDED를 확인했다.
- 일반 진단은 접수 17 / 작업 16, 강제 진단은 접수 18 / 작업 17. 첫 실행은 접수 16 / 작업 15.

## 비교 범위와 조건

- V1과 같은 사진 2장·소견·에러 코드·제품 ID를 사용했다. 사진 해시는 `입력사진해시.json`에 보관한다.
- V1 코드는 수정하지 않았다. DB는 백업 후 별도 repair-v2 볼륨으로 복원했고 최신 마이그레이션을 적용했다. V1 DB는 중지 상태로 보존한다.
- V2에는 팀원의 제품 유형·RAG 데이터·기타 변경도 포함되어 있다. 따라서 시간 차이 전체를 내 최적화만의 효과라고 해석하지 않는다.
- 위 시간은 각 실행의 관측값이며 반복 평균이나 성능 보장값이 아니다. 최적화 전 V2 중간 버전은 이번 요청에 따라 따로 실행하지 않았다.
- 리포트 생성 성공과 부품 요약 유지를 확인했으며 진단 내용의 정확도 동등성을 정량 평가한 것은 아니다.
- V1 DB에 남았던 과거 미완료 이벤트 2건은 복제 후 재발행되어 새 계약 검증에서 DLT 처리됐다. 이번 신규 진단 측정에는 포함하지 않는다.

## 코드 검증

- V2 전용 환경에서 워커 테스트 177개 통과.
- RAG 정규화 전달·최종 소견 테스트 22개 통과.
- 한 GPT 응답의 도구 요청이 1개 또는 2개인 경우 모두 총 조회 4회 뒤 정상 요약을 확인했다. 조기 요약이면 불필요한 추가 호출이 없다.
- 실제 강제 검증 후 일반 워커로 복원했다.
